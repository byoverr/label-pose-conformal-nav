## 2026-10-03 (сб), день 1

- Данные: OSMa-Bench, ReplicaCAD, 22 сцены, на HuggingFace опубликовано только условие освещения
  `baseline` (кадры 640×480, 1636 кадров в apt_0). Качаем каждый 8-й кадр (RGB, depth, semantic):
  около 15 МБ на сцену. `hf_hub_download` давал ~3,5 с на файл; прямые HTTPS-запросы в 8 потоков — ~5 файлов/с.
- Конвенция поз проверена (`scripts/check_poses.py`): `traj.txt` — матрица камера→мир, оси камеры OpenCV
  (x вправо, y вниз, z вперёд). Медианное расстояние между облаками соседних кадров: 2,1 см против 21,4 см
  (оси OpenGL) и 12,7 см (обратная матрица). Мир — как в Habitat: y вверх, пол на y = 0, камера на 1,65 м.
- apt_0: длина траектории 33,9 м; вид сверху — `results/figures/apt_0_topdown.png`.
- Глубина: uint16 / 6553,5 = метры, 0 = нет данных.
- Классы на уровне пола (y < 0,05 м): floor 76 %, rug 18 %, mat 1,5 % — это проходимая поверхность.
  В полосе препятствий (0,1–1,8 м) больше всего wall (39 %), blinds, door, cabinet. Отдельного класса
  потолка нет: выше 2,5 м всё размечено как wall.
- Эталонная 2D-сетка (`src/s2m/grid.py`, `scripts/show_gt_grid.py`): 5 см на клетку, apt_0 — 275×160 клеток,
  строится за 1,4 с на CPU; свободно 35 %, занято 22 %, неизвестно 43 %; в занятых клетках 45 классов.
  Тот же накопитель потом используется для карт с метками детектора и с дрейфом поз.

### Восприятие и карты
- Детектор: YOLO-World v2-s (Ultralytics), 98 текстовых запросов — словарь ReplicaCAD без структурных
  классов (other, floor, wall, ceiling). Текстовые эмбеддинги CLIP вшиты в веса один раз
  (`models/yolov8s-worldv2-vocab98.pt`, 26 МБ), сам CLIP (338 МБ) после этого не нужен.
  На MPS: 24 мс на кадр, около 38 детекций на кадр при пороге 0,05.
- Рамка → пиксели: внутри рамки берутся пиксели с глубиной в пределах 0,25 м от медианной глубины рамки.
- Слияние в карту — усреднением (а не наивным Байесом, который делает карты переуверенными):
  p_k(клетка) = сумма уверенностей класса k / число наблюдений в клетке.
- apt_0 при истинных позах: у 92,3 % занятых клеток есть детекция; mIoU по 32 классам — 0,25.

### Дрейф позы (`src/s2m/drift.py`, `configs/drift_levels.yaml`)
- Одометрия с шумом на каждом шаге, только в плоскости пола (x, z, рысканье); камеры в ReplicaCAD
  горизонтальны (проверено), поэтому высота, крен и тангаж точны.
- Уровни откалиброваны один раз на apt_0 (путь 33,7 м) и применяются ко всем сценам без изменений:
  L1 ATE 0,6 см; L2 3,0 см; L3 9,5 см; L4 63 см (2,8 % пути); L5 3,5 м (16,4 % пути, стресс-тест).
- Момент запроса — последний кадр; система координат планировщика — «дрейфующий мир» в этот момент.

### Dev-сцена и выбор классов
- apt_0 — dev-сцена: на ней принимаются решения по дизайну; в калибровку и тест не входит.
- Класс «stair» исключён из запретных по dev-сцене: это область 5 м², а не объект; детектор её не
  локализует (медианная уверенность 0,03), и промах около 2 м доминировал бы во всех счётах.
  Запретные классы: indoor_plant, tv_stand, bike (есть во всех сценах).
- След объекта — занятые клетки, где у класса ≥ 2 эталонных точек (раньше без условия занятости,
  из-за чего счёт по меткам был «непокрываемым» даже без дрейфа).
- Первые числа (apt_0): счёт по меткам при L0 = 1,0 (часть клеток объекта детектор не покрыл, т. е.
  калибровка только по меткам вынуждена считать запретной любую занятую клетку); при любом дрейфе
  — непокрываемо. Счёт промаха при λ = 0,05: L0 0,35 м, L3 ~0,4 м, L4 0,65–1,1 м, L5 — потолок 3 м.

### Первый анализ покрытия (v1, 15 сцен) и что из него следует
- В v1 гарантия была одна на все запретные классы сразу. Совместная ветка отказывалась в 83 % разбиений
  (радиус упирался в потолок 3 м). Причина — не ошибка кода: в двух сценах из 15 детектор уверенно принял
  тумбу под ТВ за другой класс (v3_sc0_staging_12 — «bench», промах 5,6 м; v3_sc2_staging_13 — «rug», 6,5 м).
  2/15 = 13 % > α = 10 %, поэтому при α = 0,1 честный ответ CP — «тумбу с этим детектором не гарантировать».
- Условное покрытие «когда ветка не отказалась» (0,6) — смещённая оценка: отказ выбирает удачные разбиения.
  Безусловно (отказ = пустая, но верная гарантия) покрытие ≈ 0,93. С v2 отказ считается выполненной гарантией
  и показывается отдельно.
- Покадровая CP меток (как у Sundarsingh и др., но на сетке 5 см) вырождается: часть клеток объекта детектор
  не «красит», счёт = 1, порог λ* = 0, т. е. запретным считается всё занятое. При дрейфе — непокрываемо.
- Проверена и отброшена идея «семантической окрестности» класса по сходству текстовых эмбеддингов CLIP:
  сходства почти не различают классы (bike–picture 0,86, tv_stand–bench 0,79), окрестность выродилась бы.

### Изменения дизайна (v2)
- Гарантия — по каждому запретному классу отдельно (Mondrian по классу). Один плохо распознаваемый класс
  больше не обнуляет гарантию для остальных.
- Все ветки, кроме справочной покадровой CP меток, используют одну область A_λ0(k) и различаются только тем,
  на чём калибруется радиус: метки (истинные позы), поза (эталонные метки + дрейф), их сумма, совместно.
- Деление по Бонферрони (α/2 + α/2) при α = 0,1 требует ≥ 19 калибровочных сцен — неприменимо, отмечено в отчёте.
- Миссии: параметры для сцены калибруются на всех остальных сценах (leave-one-scene-out); два фолда давали
  7 калибровочных сцен, а при α = 0,1 нужно ≥ 9. Если сертификат класса отказывает, запасной вариант —
  «всё занятое считается этим классом» с радиусом «только поза»; правило одно для всех веток.
- Исправлена невоспроизводимость: зерно генератора строилось через hash(строки), который в Python меняется
  от запуска к запуску; теперь zlib.crc32.
- Задачи миссий переделаны: цели — точки в 0,7–1,2 м от запретного объекта (а не семантические цели, которые
  смешивали ошибки целей с изучаемой гарантией и не нагружали запретные зоны: в v0 нарушений не было ни у кого).
- Оказалось, что скачаны все 22 сцены: у шести траектории короче (836–1278 кадров), ранняя проверка полноты
  срабатывала до окончания загрузки.

### Финальные результаты (v2, 21 сцена + dev, 200 разбиений, n_cal = 13, α = 0,1)
- Покрытие по классам (`results/tables/coverage.csv`). Велосипед: без калибровки ≤ 0,01; покадровая CP меток
  1,00 → 0,73 (L2) → 0,17 (L4); «только метки» 0,93–0,94 на L0–L3, 0,76 на L4; «только поза» ≤ 0,22 до L3;
  «раздельно» 0,97–0,99 при радиусе до 1,61 м (L4); «совместно» 0,93–0,94 на L0–L4 при радиусе 0,75 → 1,18 м.
  Растение — то же, но с долей отказов около 0,6. Тумба — отказ 0,71–0,95 (подмена класса в 2 сценах из 21).
- Эффект композиции проявился как переплата раздельной схемы (+36–38 % радиуса на L4), а не как недопокрытие:
  синтетический дрейф не коррелирован с ошибками детектора.

### Миссии: переделка задач
- Задачи «подъезд к объекту» (цель в 0,7–1,2 м от запретного объекта) оказались вырожденными: откалиброванная
  запретная зона ≈ 1,3 м накрывает саму цель, и при запасе m = 1 решаемы лишь 11 % задач. Перешёл на задачи
  «проезд мимо»: старт и цель ≥ 1,5 м от запретных объектов, кратчайший геометрический путь проходит ближе 0,5 м
  к растению или велосипеду. Старые результаты — в `results/archive/` (вне git).
- Падение скрипта на сценах без задач (пустой CSV) исправлено: пишется файл только с заголовком.
- Две конфигурации: основная — растение + велосипед (тумба — обычное препятствие; решение принято ПОСЛЕ анализа
  покрытия, это оговорено); системная — все три класса (запасной вариант для тумбы почти обездвиживает робота).
- Итог (растение + велосипед, 233 задачи в 15 сценах): без калибровки 27–37 % путей нарушают безопасное
  расстояние; все откалиброванные ветки — 0 нарушений, но путь находится лишь в 27–32 % задач (оракул — 98–100 %).
  Совместная против раздельной: на L3 30 % против 27 % задач с путём, длина 1,05 против 1,08 от оракула.
- H4: Spearman(mIoU сцены, доля нарушений) = −0,16 (p = 0,57, 15 сцен).

### Мост к планировщику ВКР
- Угловая зона по опубликованному правилу (конус расширяется, пока образцы попадают в препятствие) на картах со
  смещёнными проходами почти не расширяется: в синтетическом тесте 0/20 против 17/20 у равномерного RRT-Connect.
- Модификация «расширять конус после заблокированного расширения дерева, сужать после успешного» — 12/20.
- На откалиброванных картах (растение + велосипед, L2): опубликованное правило требует в 2,0–2,9 раза больше
  расширений, модификация — в 1,1–1,4 раза, и даёт самые короткие первые пути (1,11–1,15 от кратчайшего против
  1,15–1,21). Решаемость за бюджет у всех трёх одинакова в пределах нескольких п. п.; ограничивает свободное
  пространство (при откалиброванном запасе решаемы 30 % задач против 97 % без запаса).

## 2026-10-03, вечер: проверка упрощений («сделать по красоте»)

### Уровень риска α
- Миссии и покрытие пересчитаны при α = 0,05 / 0,2 / 0,3 (`results/missions_pb_a*`, `results/tables/coverage_a*.csv`,
  `scripts/analyze_alpha.py`).
- Совместная ветка держит номинал при каждом α.
- Радиус при росте α с 0,1 до 0,3 убывает медленно: растение 0,81 → 0,60 м, велосипед 0,75 → 0,50 м (L3).
  Решаемость миссий почти не растёт: 30 → 31 %. Вывод: упираемся в «пол» ошибки восприятия, а не в уровень риска.
- Отказы по растению исчезают при α ≥ 0,2 (сцена с пропущенным растением перестаёт определять квантиль).

### Стресс-тест композиции
- Ошибки меток реальные, поза — сценовая смесь: в k сценах из 21 реализации L5 («отказ локализации»), в остальных L1.
  Сцены с отказом выбираются тремя способами:
  - согласованно — где метки хуже всего;
  - разнесённо — где метки лучше всего;
  - случайно.
- α = 0,3: при α = 0,1 и n = 13 квантиль равен максимуму, редкие отказы всегда попадают в радиус, и эффект не виден в принципе.
- Раздельная схема: 0,80–0,84 при согласованных отказах и до 0,66 при разнесённых (номинал 0,70, растение);
  совместная — 0,71–0,78 везде. Это первое прямое наблюдение недопокрытия суммы квантилей.
  Теория: сумма квантилей гарантирует лишь 1 − 2α (неравенство Буля).

### Маски MobileSAM
- Рамки → маски MobileSAM (`BoxSegmenter`, кэш на сетке шага 4: `save_masks` / `load_masks`, 1–2 МБ на сцену).
- Медианный промах велосипеда при L0: 0,43 → 0,05 м, максимальный не изменился (0,75 м).
- При n = 13 и α = 0,1 квантиль равен максимуму, поэтому радиус велосипеда не изменился; растения — 0,85 → 0,61 м.
- Вывод: при малом числе сцен запас определяет наихудшая сцена, улучшать нужно хвост ошибок восприятия.
- Ошибка в коде: кадр без детекций давал `reshape(0, -1)`. Исправлено явной формой.

### Реальная одометрия
- Open3D RGB-D odometry (гибридный член, параметры по умолчанию, начальное приближение — постоянная скорость),
  кадр к кадру, без замыканий циклов.
- На каждом 8-м кадре (повороты на месте по 16° за шаг) одометрия срывается: ATE 12,7 м на apt_0.
  Пришлось скачать каждый 2-й кадр (RGB + глубина, ~0,9 ГБ, `data/replica_cad_vo`).
- Свободная 6-DoF ВО на apt_0 один раз «опрокинулась» (наклон 89° у стены вплотную при повороте).
  Добавлено плоское ограничение наземного робота (`planar_motion`): каждое относительное движение проецируется
  на рысканье + сдвиг по полу. Итоговая ошибка тоже планаризуется (`planarize`): высота и наклон известны по IMU.
- Параметры ВО НЕ подбирались по истине: перебор на apt_0 показал, что ни одна настройка не лучше во всех
  трудных местах, а выбор по GT был бы подгонкой под тест.
- Попутно: своп при 8 параллельных процессах занял диск (осталось 300 МБ), сессия упала.
  Очищены кэши pip и Go (~1 ГБ); теперь не больше 3–4 тяжёлых процессов.
- Итог ВО по 21 сцене: ATE от 3,5 см до 3,9 м, медиана 78 см; дрейф в конце 1–27 % пути.
  Каждый 4-й кадр: медиана 2,6 м, режим «потерянной локализации».
- Калибровка (n_cal = 13, α = 0,1):
  - «только метки»: 0,67 (велосипед), 0,74 (растение) — ложный сертификат;
  - совместная: 0,93–0,96, но отказ в 60 % (велосипед) и 86 % (растение) разбиений.
- Миссии на ВО (216 задач со стартом и целью в пределах карты):
  - без калибровки путь в 23 % задач, из них 44 % нарушают и 38 % проходят через препятствия;
  - совместная отказывается в 89 % задач.
- Вывод: без замыканий циклов полезной гарантии нет, и совместная калибровка честно это сообщает.
